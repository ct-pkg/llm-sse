- 三个依赖是否已发布出可消费单元、许可是否可兼容，**本轮未核对**（可用 `ct get` 与发布索引查），需求规约 §5.2 仍按上一次核对记录记为依赖侧阻塞。

## 2 待办

### 2.1 清单补齐归属与命名空间根，依赖改全名

- **为什么需要**：`publisher` 与 `ns-root` 是必填项，不写进清单就打不了包；`ns-root` 还决定 include 根怎么展开。三条 `dep` 只写短名时无法表达发布方与版本范围，多发布者下会撞名。
- **要做什么**：
  1. `ct.pkg` 增补 `publisher`、`ns-root`；
  2. 三条 `dep`（http / sse / json）从短名改为「发布者/包名@版本范围」；
  3. 头部注释同步去掉「三条 dep 有意不带版本」的说法（见 3.1）。
- **前置条件**：无。原记的前置（包管理器读不到 `publisher`、`ns-root` 不进 include 解析）已作废，两项能力均已具备。
- **验收方式（现在即可执行）**：
  1. `ct.pkg` 含 `publisher`、`ns-root`，值非空；
  2. 三条 `dep` 均为「发布者/包名@版本范围」，`grep -E '^dep = (http|sse|json)$'` 0 命中；
  3. 打包后 store 内路径按「发布方 / 包名 / 版本」分层出现本包；
  4. 生成的 lock 里能读到本仓的发布方与单元根；
  5. 构建不手写绝对 `-I` 也能解析到 `ns-root` 下的单元；
  6. 反向判据：缺 `publisher` 或 `ns-root`、或任一 `dep` 仍是短名 → 本条未完成。
- **状态**：「要做什么」第 1、2 项已改到工作区（未提交）；验收第 3–5 项未实跑；「要做什么」第 3 项（头部注释同步）未做。

### 2.2 公开单元按「规格占位」处理

- **为什么需要**：本包要对外可用，必须有可消费的公开符号；但实现未开始，现在补了也验证不了。折中做法是把「本包当前只有规格」写成明确状态，避免对外声称可用。
- **要做什么**：明示无公开单元，状态登记 `dormant`，不打 tag；将来立项时再决定是否补公开单元。
- **前置条件**：取决于本仓有没有 `src/`，与包管理器能力和依赖就绪程度无关。
- **验收方式**：
  - 占位期：README 状态行仍写「未立项 / 依赖未就绪」，仓库无示例、无 tag，无声称可用的公开面；
  - 转实现时：生成头的导出符号与需求规约 R-F-02 的冻结清单脚本比对 0 差异。
- **状态**：`dormant`（规格占位已落定）。

### 3.2 工作区未提交的 `ct.pkg` 改动

- **现状**：`ct.pkg` 的 `requires` 已抬到当前最新发布版，注释改写为「以最新发布版为下限，功能性下限是方法级 `pub`（默认私有），用于把 helper 挡在生成头之外」。该改动**未提交、也未丢弃**，本轮不碰它。
- **待决**：
  1. `requires` 下限口径：写「跟着最新发布版走」不可核对，且随上游每次发版漂移；建议改为「按本包实际用到的最小能力集」并指名是哪一项能力（方法级 `pub` 默认私有），不写版本号；
  2. 头部注释与正文同步（见 3.1）；
  3. 环境结论更正：`command -v ct` 为空，但 `~/.local/bin/ct` 实测可执行。需求规约 §5.3 已改判，原「环境阻塞」取消；本文件不再复述该结论。

### 3.3 依赖可消费性核对

- **为什么需要**：需求规约 §4 里 C / D 组与 B 组若干条的级别是「外部阻塞（依赖侧）」，依据是上一次读依赖仓源码的记录，不是本仓能维护的事实。
- **怎么核对**：用 `ct get` 解析三个依赖的 spec，再看发布索引的六字段（发布方、包名、版本等）与许可字段；不需要读依赖仓源码。
- **本轮结论**：只重判文档，**未跑该命令**，故 §4 的阻塞列不改；核对后若已可消费，再按条改判并同步 §5.2。
- **不做的**：为了让判据转绿把 `dep` 指向假包、把依赖源码 vendored 进本仓、或把端到端判据标 skip。
