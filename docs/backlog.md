# 包清单与发布面待办

> 本文件只记本仓自己的事：清单要补什么、公开面怎么处置、卡在哪个待决口径上。不引用外部阶段划分与版本号，分期判断由本仓按现状自行作出。

## 1 本仓判断

**现状（事实）**

- 需求层梳理完成，**未立项**：无 `src/`、无公开单元、无 phase 卡、无门禁脚本、无 tag。
- `ct.pkg` 只有 name / version（0.1.0）/ licence / 三条短名 `dep` / `requires`，没有 `publisher`、没有 `ns-root`。
- 三个依赖都没有本包可消费的发布面，所以依赖相关判据当前一条也转不了绿。

**据此作出的分期判断**

| 事项 | 现在做吗 | 理由 |
| --- | --- | --- |
| 清单补 `publisher` / `ns-root`、依赖改全名 | 不现在做，先记为待办 | 属清单与发布面改造，只在包管理器真的能读 `publisher`、能把命名空间根纳入 include 解析之后才有可核对的对象；在此之前改完也无法验证，改了只是自说自话 |
| 补公开单元 | 不单独做，随首个立项 phase | 公开面必须有可执行的导出符号清单才能验收，而导出符号依赖实现；未立项、无 `src/` 时无从谈起 |
| 单独为这两件事立 phase | 不立 | 本包未立项，phase 号尚未分配；且现在能给出的判据只有「文件可核对」级，达不到立 phase 要求的可执行退出判据。等依赖面具备、能有第一条可跑断言时再随首个 phase 一并排期 |

**完成到什么程度**：公开面已按「规格占位」落定口径（见 2.2），清单改造未开始（见 2.1）。**还要不要继续往前推**：两项都不推，等 2.1 的前置条件成立。

## 2 待办

### 2.1 清单补齐归属与命名空间根，依赖改全名

- **为什么需要**：包一旦要按命名空间被安装和引用，清单必须自报归属（`publisher`）与命名空间根（`ns-root`）；三个依赖若只写短名，在存在多个发布者时会撞名，也无法表达版本范围。
- **要做什么**：
  1. `ct.pkg` 增补 `publisher`、`ns-root`；
  2. 三条 `dep`（http / sse / json）从短名改为「发布者/包名@版本范围」形态。
- **前置条件（一句话）**：包管理器能读到清单里声明的 `publisher` 值，并能把 `ns-root` 交给 include 解析 —— 目前这两项能力都没有，所以本条不动手。
- **验收方式**：
  1. `ct.pkg` 含 `publisher`、`ns-root`，值非空，且与包管理器实际读到的值一致（前置满足后核对）；
  2. 三条 `dep` 无短名残留（可 grep 核对）；
  3. 声明了 `ns-root` 的 include 能解析到依赖，构建不因命名空间缺失失败；
  4. 反向判据：任一 `dep` 仍是短名，或 `publisher` / `ns-root` 缺失 → 本条未完成。
- **状态**：未开始。

### 2.2 公开单元按「规格占位」处理

- **为什么需要**：本包要对外可用，必须有可消费的公开符号；但依赖面未就绪，现在补了也验证不了。折中做法是把「本包当前只有规格」写成明确状态，避免对外声称可用。
- **要做什么**：明示无公开单元，状态登记 `dormant`，不打 tag；将来立项时再决定是否补公开单元。
- **验收方式**：
  - 占位期：README 状态行仍写「未立项 / 依赖未就绪」，仓库无示例、无 tag，无声称可用的公开面；
  - 转实现时：生成头的导出符号与需求规约 R-F-02 的冻结清单脚本比对 0 差异。
- **状态**：`dormant`（规格占位已落定）。

## 3 待决项

### 3.1 `dep` 是否一律改成全名带版本范围

三种口径目前并存，本仓不预设立场，收敛前 2.1 不落地：

| # | 出处 | 当前口径 |
| --- | --- | --- |
| 1 | `ct.pkg` 头部注释 | 三条 `dep` 有意不带版本，因为三个依赖都还没有本包可消费的发布面 |
| 2 | 本文件 2.1 | 三条 `dep` 一律写成「发布者/包名@版本范围」 |
| 3 | 需求规约 R-F-01 | `dep` 只要求出现 http / sse / json 短名 |

需要定的只有一件事：以哪一条为准，另外两条是否随之改写。

### 3.2 工作区未提交的 `ct.pkg` 改动

- **现状**：`ct.pkg` 的 `requires` 已抬到当前最新发布版，注释同步改写为「以最新发布版为下限，功能性下限仍是方法级 `pub`（默认私有），用于把 helper 挡在生成头之外」。该改动**未提交、也未丢弃**。
- **待决**：
  1. 这个下限值是保留，还是等依赖面就绪后按可消费能力重新定；
  2. 需求规约 §5 记「本机 `command -v ct` 为空」，而实测在 `PATH` 之外的目录里存在可执行的 `ct`，该条环境阻塞结论需要重判。
